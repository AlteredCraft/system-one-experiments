EXP-04 · model-router · first live run · 2026-10-08

Three Jevs pick the model for 24 sub-agent tasks.

One request to a System One model decides whether a sub-agent runs on Haiku, Sonnet or Opus. We asked three different Jevs, a hosted one and two running on a laptop, to make that call for the same tasks. On the scoreboard they nearly tie. Underneath, they differ a lot in how sure they are and how fast they answer.

01

The problem: every sub-agent gets the same model

An agent harness spawns sub-agents all the time: find the callers of a function, add a flag, chase down a memory leak. Either the orchestrator spends its own tokens deciding which model each one gets, or everything runs on the most capable model. model-router makes that choice with one call, just before the spawn.

in Orchestrator spawns a task "Checkout intermittently double-charges customers. Find the cause."
1 · code Pinned? The task names a model → use it, ask nothing.
2 · code A rule? e.g. agent type Explore → lookup.
3 · Jev One Score question A probability for each kind of work.
4 · code Policy The cheapest route whose risk ≤ the bar.
out A model from the config haiku sonnet opus

Fig. 1This run skipped steps 1 and 2 so that every task was judged by the model. If the decision model fails or times out, the router returns the config's fallback route and never throws.

02

Hypothesis, and what would confirm it

Hypothesis One Jev call over the text of a sub-agent task chooses a model tier well enough that a harness can move a large share of sub-agent work off its most capable model, while rarely sending a task to a model too weak for it, at a latency that is small next to starting the sub-agent.

03

The three decision models

Same API, same question, same 24 tasks, each asked once. One model is hosted by TypeSafe; two are Open Jev models running 4-bit on an Apple M5 Pro laptop. Flash 9B was released the day before this run.

04

What Jev was asked

Each request carries the task text and one Score question. The levels describe kinds of work, cheapest first. Each maps to a model in the router's config, and Jev never sees a model name: it can judge what a task asks for, but knows nothing about what claude-haiku-5-5 is good at.

Which description fits the work that task asks a sub-agent to do?

    05

    How an answer becomes a route

    Jev returns three probabilities that add up to 1. The obvious policy takes the biggest. The router asks something different of each route: if the task is sent here, how likely is it that it needed a more capable model? That's the sum of everything above it. It takes the cheapest route where that risk is at or under the bar. Sending a task too low costs a failed run and a retry; too high only costs money.

        10

        What this does and doesn't show

        Read it as "the mechanism works", not as a measured accuracy.

        It shows
        • The request works end to end on all three decision models.
        • A Score over route descriptions separates clear cases.
        • A model a third of the size can do the job in a third of the time, when the routing rule allows for its doubt.
        • The policy can be tuned after the fact without asking again.
        It doesn't show
        • 24 tasks, asked once each. One task is 4 percentage points.
        • One author wrote everything. The tasks, their labels and the route descriptions came from one sitting, so tasks echo the wording they're judged against ("find the cause" against "a failure with an unknown cause").
        • Labels are opinions. Nobody ran these tasks on the three Claude models to see which was enough. That needs a harness (check 4).
        • Flash 9B's 24 of 24 has little margin. On tasks 13 to 16 it was close to an even split between two routes.
        • The tasks don't separate the models. All three are at or near 24 of 24, so this says nothing about which decides best.
        Next, from the README's Open list
        1. Replace the starter tasks with ≥ 100 sub-agent prompts from real harness sessions, labelled by the model that turned out to be enough.
        2. Wire it into a harness's spawn path and log each decision with the sub-agent's outcome.
        3. Try a second question for work the tiers don't order, such as "the task needs to read images".
        4. Compare with the orchestrator choosing the model itself: agreement, and the tokens it spends deciding.
